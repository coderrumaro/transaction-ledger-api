# Transaction Ledger API

A small backend API for a transaction ledger. You can create accounts, post credit/debit transactions, check balances, view paginated transaction history and transfer money between accounts.

Built with Node.js, Express, TypeScript and PostgreSQL.

## Requirements

- Node.js 18+
- PostgreSQL 13+ (uses `gen_random_uuid()`)

## Setup

1. Install dependencies

```bash
npm install
```

2. Create a database and a user (or use your own and change `DATABASE_URL`)

```bash
psql -U postgres -c "CREATE USER ledger WITH PASSWORD 'ledger'"
psql -U postgres -c "CREATE DATABASE ledger OWNER ledger"
```

3. Create the env file

```bash
cp .env.example .env
```

4. Create the tables

```bash
npm run db:init
```

5. Start the server

```bash
npm run dev
```

The API runs on `http://localhost:3000` by default. For a production style run use `npm run build` and then `npm start`.

## API documentation

Swagger UI is available at `http://localhost:3000/docs` once the server is running. The spec itself is in `docs/openapi.yaml`.

| Method | Endpoint | Description |
| --- | --- | --- |
| POST | `/accounts` | Create an account |
| GET | `/accounts/:id/balance` | Get current balance |
| POST | `/accounts/:id/transactions` | Add a credit or debit transaction |
| GET | `/accounts/:id/transactions` | Transaction history (`type`, `page`, `limit`) |
| POST | `/transfers` | Transfer money between two accounts |

### Examples

Create an account

```bash
curl -X POST localhost:3000/accounts -H 'Content-Type: application/json' -d '{"name": "Alice"}'
```

Credit an account

```bash
curl -X POST localhost:3000/accounts/<id>/transactions -H 'Content-Type: application/json' \
  -d '{"type": "credit", "amount": 100, "reference_id": "txn-1", "description": "Initial deposit"}'
```

Get history (debits only, 5 per page)

```bash
curl 'localhost:3000/accounts/<id>/transactions?type=debit&page=1&limit=5'
```

The history response looks like

```json
{
  "data": [],
  "pagination": { "page": 1, "limit": 5, "total": 0, "total_pages": 0 }
}
```

Transfer

```bash
curl -X POST localhost:3000/transfers -H 'Content-Type: application/json' \
  -d '{"from_account_id": "<id1>", "to_account_id": "<id2>", "amount": 30, "reference_id": "transfer-1"}'
```

### Errors

All errors have the same shape

```json
{ "error": { "code": "INSUFFICIENT_BALANCE", "message": "Account does not have enough balance" } }
```

| Status | Code | When |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Bad body, type, amount, account id or pagination params |
| 404 | `ACCOUNT_NOT_FOUND` | Account does not exist |
| 409 | `DUPLICATE_TRANSACTION` | `reference_id` already used for the account |
| 422 | `INSUFFICIENT_BALANCE` | Debit/transfer is more than the balance |

## How data integrity is handled

- Every transaction runs in a DB transaction. The account row is locked (`SELECT ... FOR UPDATE`), the balance is updated and the transaction row is inserted, then committed. If anything fails it is rolled back.
- `accounts.balance` has a `CHECK (balance >= 0)` and `transactions` has `UNIQUE (account_id, reference_id)` and `CHECK (amount > 0)`.
- There are no update or delete endpoints for transactions, and a database trigger also rejects `UPDATE`/`DELETE` on the `transactions` table.
- Transfers lock both accounts (ordered by id to avoid deadlocks) and write the debit and credit in one DB transaction.

## Assumptions

- Account ids and transaction ids are UUIDs generated by the database.
- Single currency, amounts are positive numbers with at most 2 decimal places.
- A balance can never go below 0, so overdrafts are not supported.
- A repeated `reference_id` on the same account returns `409` with the existing transaction in the response, and nothing is changed. The same `reference_id` can be used on different accounts.
- A malformed account id (not a UUID) returns `400`, a well formed id that does not exist returns `404`.
- Transaction history is sorted by `created_at` descending. Defaults are `page=1` and `limit=10`, max `limit` is 100. A page past the end returns an empty list.
- For a transfer, the same `reference_id` is used for the debit on the source account and the credit on the destination account. It also fails with `409` if the `reference_id` is already used on either account.
- There is no authentication, since it was not part of the requirements.
